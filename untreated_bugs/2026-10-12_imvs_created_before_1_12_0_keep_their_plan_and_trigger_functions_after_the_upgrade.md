# After `ALTER EXTENSION pg_reflex UPDATE TO '1.12.0'`, IMVs created before keep their create-time plan and trigger functions: defects fixed in 1.12.0 stay, and writes addressed to a partition are lost until `reflex_rebuild_triggers` — S1 (SILENT wrong result, upgrade hazard)

Observed in the real upgrade run of the 1.12.0 packaging (`packaging-report.md` §4.4 in the
ledger `.superpowers/sdd/2026-10-07-1.12.0-create-contract-hardening/`): PostgreSQL 17.11, a
throwaway instance, 1.11.5 installed from a `git archive 6946400` export, then the 1.12.0 library
and `ALTER EXTENSION pg_reflex UPDATE TO '1.12.0'`. The release notes tell the user to recreate
every IMV; this report records what happens to the user who does not, or who recreates only some.

Grouped here because the cause is one: the migration replaces the extension's own functions, but
what a create stored (the plan, the relevant columns, the key mappings, the spellings, the
column types, the per-source trigger functions) is not regenerated. Related, older and narrower:
`2026-10-01_migration_trigger_regeneration_silently_noop.md`.

## Reproduction

The packaging report gives the run as prose, not as a script. Fixture: eight IMVs created on
1.11.5 (grouped, keyed passthrough, `ROUND(AVG)`, DEFERRED, one calling an unlabelled function,
two over a LIST-partitioned source `sales`, one over a table that has a namesake in another
schema). Bidirectional oracle on 1.11.5: `ROUND(AVG)` wrong (3 of 3 rows), the others 0.

Then `ALTER EXTENSION pg_reflex UPDATE TO '1.12.0'` (`extversion` 1.12.0, the drop hook's
`prosrc` equal to a fresh `CREATE EXTENSION`, both event triggers enabled,
`reflex_ivm_status()`: 8 rows, none stale), and with **no IMV recreated**:

| Observed | |
|---|---|
| The IMVs stay maintained on ordinary writes | as before |
| The `ROUND(AVG)` IMV | stays wrong |
| An INSERT addressed to a partition of `sales` | lost, no error, until `reflex_rebuild_triggers('sales')` (`rebuilt 8 trigger DDL(s)`: six triggers on the source and on each partition) and `reflex_reconcile`; afterwards a partition INSERT and a partition TRUNCATE are followed |
| One IMV of `orders` recreated, the others not | `__reflex_trunc_trigger_on_orders` kept its 1.11.5 body until `reflex_rebuild_triggers('orders')` |
| All dropped (`drop_reflex_ivm(name, true)`, `graph_depth DESC`) and recreated | every oracle 0 after writes, a new partition and a partition TRUNCATE; `reflex_audit()`: `OK (8 IMV(s), 4 source(s) checked, no findings)` |

## Expected vs actual

Expected: after the upgrade, either the old IMVs behave as 1.12.0 documents, or something
(`reflex_audit`, `reflex_doctor`, a NOTICE of the migration) names the IMVs that still run on
1.11.5 artefacts. Actual: `reflex_ivm_status()` reports none stale and the run shows no finding
for them; the user learns it from the release notes only.

## What is established and what is not

Established on the upgraded instance: the table above, and nothing more.

Read from the code or from branch reports, **not** observed on an upgraded instance:
- an IMV created before the upgrade that nests `AVG` / `SUM` / `FILTER` in an expression stays
  wrong; `reflex_reconcile` and `reflex_rebuild_imv` are said not to repair it and the audit and
  doctor to stay silent (task-4b review, I2). The packaging report says explicitly that whether
  `reflex_reconcile` repairs a 1.11.5 `ROUND(AVG)` IMV **was not tried** (doubt 5);
- the fixes for a partition change plus a partition TRUNCATE in one transaction apply only once
  the source's truncate function is regenerated by `reflex_rebuild_triggers`
  (`full-review-r3-fix-report.md`, "Migration impact");
- the folding of an upper-case column reference or a quoted alias happens at create only, and
  nothing detects an IMV stored with the old spelling (G5 residual);
- a registry that holds one relation under two spellings (created before the spellings were
  unified) has no repair path short of dropping and recreating both IMVs (G1b review, N2);
- IMVs created by a version that stored sources of other schemas without their schema stop being
  matched by the per-schema lookups (`p3-c-report.md` R2.9).

Not established: what `reflex_audit()` and `reflex_doctor()` print on the upgraded, not recreated
instance (the report gives the audit line only after the recreate); which of the items of the
second list a `reflex_rebuild_triggers` alone repairs.

## What was ruled out

- Not a failed migration: the installed migration equals the file, the drop hook equals a fresh
  install.
- The recreate-all path works and ends clean.

## Fix direction (hypothesis to falsify)

Record the extension version an IMV was created with (a registry column, bootstrap and
migration), and have `reflex_audit` report every IMV whose version is older than the last one
that changed stored artefacts, with the remedy `reflex_rebuild_chain` (or drop and create) and,
for the per-source functions, `reflex_rebuild_triggers('<source>')`. The remedy must be shown to
clear the finding, which it does not for a definition 1.12.0 refuses: see
`2026-10-12_reflex_rebuild_imv_and_chain_fail_on_an_imv_whose_definition_1_12_0_refuses.md`.
Alternatively have the migration call `reflex_rebuild_triggers` for every registered source; the
older report above describes why a migration-time regeneration silently did nothing once.
