# Inner workings

This page is the **operation-by-operation reference** for incremental maintenance: for every supported shape and every DML operation, exactly what SQL pg_reflex emits and in what order. It is the detailed companion to two shorter pages:

- [Delta processing](delta-processing.md) — the five-step mental model (short-circuit → predicate → lock → MERGE → refresh).
- [Internals](internals.md) — engine behaviours (trigger model, HOT, fillfactor, partitioning, lock table).

Here we go one level deeper and walk the codegen. Everything below is generated by `reflex_build_delta_sql` (`src/trigger/mod.rs`) and the builders in `src/trigger/{ops,merge,dispatch,scope,deferred}.rs`. SQL fragments use generic placeholders — `<view>` (target), `<intermediate>` (`__reflex_intermediate_<view>`), `<scratch>`, `<affected>` (`__reflex_affected_<view>`), `<shrunk>`, and the per-source transition tables `<new>` / `<old>`. Real identifiers are schema-qualified and quoted; the spine is what matters.

!!! note "Where the work runs"
    All of this executes inside the **writer's `AFTER STATEMENT` trigger** (IMMEDIATE mode) or at **COMMIT** (DEFERRED mode). The emitted statements are concatenated into one PL/pgSQL body, separated by a `--<<REFLEX_SEP>>--` marker, and the trigger loop `EXECUTE`s them one at a time. A per-`(view, source, op, queries)` LRU cache (`DELTA_SQL_CACHE_MAX = 256`) memoises the generated SQL so codegen runs once per distinct shape, not once per flush.

---

## 1. How a flush is routed

When a tracked source is mutated, the statement trigger fires once with the full transition table and loops over every enabled IMV that depends on the source (ordered by `graph_depth`, so parents flush before children). For each IMV it runs, in order:

1. **Empty-delta short-circuit** — `IF NOT EXISTS(SELECT 1 FROM <transition> LIMIT 1) THEN RETURN NULL`.
2. **`ignore_sources` skip** — if this source is in the IMV's `ignored_sources`, `CONTINUE`.
3. **`where_predicate` skip** — evaluate the IMV's stored `WHERE` against the transition rows; skip if none match.
4. **Directional probe** (UPDATE only) — classify the batch (e.g. a filter OUT→IN flip becomes `INSERT_PROMOTED`); see §4.3.
5. **Path B pre-scratch dispatch** — `|transition| / |source| ≥ wipe_threshold` ⇒ `reflex_reconcile` and `CONTINUE` (§5.1).
6. **Path C pre-scratch dispatch** (promoted UPDATE only) — planner row-estimate ⇒ smart bulk-INSERT (§5.2).
7. **Per-IMV advisory lock** — `pg_advisory_xact_lock(hashtext(name), hashtext(reverse(name)))`.
8. **Build + execute the delta SQL** — `reflex_build_delta_sql(...)`, then `EXECUTE` each separated statement.

Step 8 is where `reflex_build_delta_sql` picks **one** of five families by inspecting the query and operation:

| Condition (checked in this order) | Family | Section |
|---|---|---|
| Source appears 2+ times in `base_query` (`is_self_join`) | **Self-join full refresh** | [§7.2](#72-self-join-full-refresh) |
| Source is the secondary side of a LEFT/RIGHT/FULL JOIN | **Outer-join secondary** | [§7.1](#71-outer-join-secondary-tables) |
| `plan.is_passthrough` (no GROUP BY) | **Passthrough** | [§6](#6-passthrough-maintenance) |
| otherwise | **Aggregate** (GROUP BY) | [§2](#2-aggregate-maintenance-the-spine)–[§4](#4-update) |

The order matters: self-join and outer-join-secondary corrections take precedence over the normal aggregate/passthrough paths because the naïve delta would be *incorrect* for those shapes, not merely slow.

## 2. Aggregate maintenance: the spine

Every grouped IMV is maintained through the same three-table spine:

```
<scratch>     -- the delta, pre-aggregated to group grain
<intermediate>-- the running sufficient statistics (one row per group, + __ivm_count)
<affected>    -- the set of group keys this batch touched
```

The canonical incremental flush is:

```sql
-- 1. materialise the delta at group grain
TRUNCATE <scratch>;
INSERT INTO <scratch> <delta_query>;          -- base_query with source → <new>/<old>

-- 2. fold the delta into the running statistics
MERGE INTO <intermediate> t USING <scratch> d ON <null-safe key match>
  WHEN MATCHED     THEN UPDATE SET <aggregate accumulators>, __ivm_count = …
  WHEN NOT MATCHED THEN INSERT (...) VALUES (...);   -- Add only
ANALYZE <intermediate>;                        -- non-optional, see §5

-- 3. record which groups moved
TRUNCATE <affected>;
INSERT INTO <affected> SELECT DISTINCT <group_cols> FROM <scratch> __d;
ANALYZE <affected>;

-- 4. project only those groups back to the target (the epilogue, §2.4)
[DELETE FROM <intermediate> WHERE __ivm_count <= 0 AND <group> IN <affected>;]  -- dead cleanup
DELETE FROM <view>  WHERE <key> IN (SELECT <key> FROM <affected>);
INSERT INTO <view>  SELECT <projection> FROM <intermediate>
                    WHERE <key> IN (SELECT <key> FROM <affected>) AND __ivm_count > 0;
UPDATE public.__reflex_ivm_reference SET last_update_date = NOW() WHERE name = '<view>';
```

The differences between INSERT, DELETE and UPDATE live entirely in **how `<scratch>` is filled** and **how the MERGE accumulates** (add vs subtract). The epilogue (step 4) is shared.

### 2.1 The MERGE (`src/trigger/merge.rs` · `build_merge_using`)

```sql
MERGE INTO <intermediate> AS t USING <scratch> AS d
ON  t."k1" = d."k1"                       -- NOT NULL key column: plain equality (index-usable)
AND t."k2" IS NOT DISTINCT FROM d."k2"    -- NULLable key column: NULL-safe
WHEN MATCHED THEN UPDATE SET …
WHEN NOT MATCHED THEN INSERT (…) VALUES (…)   -- emitted for Add only
```

The `WHEN MATCHED` SET clause is generated per aggregate column, and the sign is `+` for `Add` (INSERT / UPDATE-new side) and `-` for `Subtract` (DELETE / UPDATE-old side):

| Aggregate | `Add` accumulator | `Subtract` accumulator |
|---|---|---|
| `SUM` | `"s" = COALESCE(t."s",0) + COALESCE(d."s",0)` | `… - …` |
| `COUNT` / `COUNT(*)` | `"c" = COALESCE(t."c",0) + COALESCE(d."c",0)` | `… - …` |
| `MIN` (no top-K) | `"m" = LEAST(t."m", d."m")` | `"m" = NULL` → recompute (§3) |
| `MAX` (no top-K) | `"m" = GREATEST(t."m", d."m")` | `"m" = NULL` → recompute (§3) |
| `MIN`/`MAX` (top-K) | sorted-merge of `"m_topk"` arrays, `LIMIT K` | `"m_topk" = __reflex_array_subtract_multiset(...)`, `"m" = NULL` |
| group bookkeeping | `__ivm_count = COALESCE(t.__ivm_count,0) + COALESCE(d.__ivm_count,0)` | `… - …` |

`AVG` is maintained as `(SUM, COUNT)` and divided in the target projection — it is never stored as a single running mean. `BOOL_OR`/`BOOL_AND` and `COUNT(DISTINCT)` carry their own sufficient statistics (see [sufficient statistics](sufficient-statistics.md)).

`__ivm_count` is the per-group source-row count. A group whose count returns to zero is **logically deleted** but physically survives the MERGE — it is removed by the dead-cleanup DELETE and excluded from the target by `__ivm_count > 0`.

### 2.2 The affected-groups table

`<affected>` is the join-pruning device for the whole epilogue. It is filled `SELECT DISTINCT <group_cols> FROM <scratch>` — i.e. only the keys the delta actually touched — and then both the target DELETE and the re-projecting INSERT are restricted to it (a semi-join, expressed as `IN (...)` or `EXISTS (...)`). This is what makes the refresh `O(affected groups)` rather than `O(intermediate)`.

### 2.3 Scalar (no GROUP BY) IMVs

When the aggregate has no group columns (e.g. `SELECT SUM(amount) FROM sales`), there is no key to match on. The MERGE matches on a constant sentinel column, there is no `<affected>` table, and the epilogue degenerates to:

```sql
TRUNCATE <view>;
INSERT INTO <view> <end_query>;
```

### 2.4 The epilogue (`src/trigger/ops.rs` · `aggregate_epilogue_stmts`)

The shared step-4 has three variants chosen by the shape of `end_query`:

- **`end_query` is a pure projection of the intermediate** (the common case): the affected-scoped `DELETE`/`INSERT` shown in §2.
- **`end_query` itself contains a `GROUP BY`** (the target re-aggregates the intermediate, e.g. a rollup): the affected-groups filter is spliced *into* `end_query` before its `GROUP BY` (`inject_affected_filter_before_group_by`); if that splice can't be formed, it falls back to a full `DELETE FROM <view>; INSERT INTO <view> <end_query>`.
- **Scalar**: `TRUNCATE`+`INSERT` as in §2.3.

For UPDATE, the epilogue does not run these statements directly — it hands the MERGE and the target sync to the **dispatcher** (§5), which decides incremental-vs-rebuild at flush time.

## 3. MIN / MAX and top-K

MIN and MAX are not invertible: subtracting the deleted rows from a running MIN can't tell you the new MIN without looking at what remains. pg_reflex handles this two ways, chosen at create time.

**Top-K heap (default, `K = 16`).** Each MIN/MAX column carries a companion array column `"m_topk"` holding the K smallest (MIN) or largest (MAX) values for the group. On `Add` the heap is a sorted-merge `LIMIT K`; on `Subtract` it is `__reflex_array_subtract_multiset(...)` (removes one copy of each deleted value). The scalar `"m"` is then refreshed from the heap top (`build_topk_scalar_refresh_sql`):

```sql
UPDATE <intermediate> SET "m" = "m_topk"[1]
WHERE cardinality("m_topk") > 0
  AND <group> IN (SELECT <group> FROM <affected>);   -- scoped to touched groups
```

As long as the group still has ≥1 value in its heap, this is `O(K)` and never touches the source. A retraction only escapes to a source scan when the **heap underflows** — the group's true cardinality dropped below K so the heap can no longer answer.

**Scoped source recompute (the underflow path, `src/trigger/scope.rs` + `merge.rs::build_min_max_recompute_sql_inner`).** When a heap is empty/short (or top-K is disabled, `topk = 0`), the group's MIN/MAX is re-derived from the base query, but **only for the affected groups**, guarded by an `EXISTS` so the scan is skipped entirely when nothing underflowed:

```sql
DO $$ BEGIN
  IF EXISTS (SELECT 1 FROM <intermediate> i JOIN <affected> a ON <key>
             WHERE i."m" IS NULL OR cardinality(i."m_topk") = 0) THEN
    UPDATE <intermediate> i SET "m" = src."m", "m_topk" = src."m_topk"
    FROM ( <orig_base_query>  WHERE <group> IN (SELECT <group> FROM <affected>) ) src
    WHERE <i.key = src.key> AND (i."m" IS NULL OR cardinality(i."m_topk") = 0);
  END IF;
END $$;
```

On **UPDATE** of a top-K column there is an extra wrinkle: an update can shrink a heap below K without nulling the scalar, so the maintenance captures the genuinely-shrunk groups into `<shrunk>` (`push_topk_shrunk_groups_capture`) and forces a recompute on exactly those after the new-side `Add` (`force_topk = true`). This is the "heap-shrinkage gate" — it keeps narrow updates off the source scan when `K ≪ group cardinality`.

## 4. The three operations in detail

### 4.1 INSERT (`aggregate_insert_stmts`)

Fill `<scratch>` from `base_query` with the source rewritten to the `<new>` transition table, MERGE with `Add` semantics (`WHEN NOT MATCHED` creates new groups), capture affected, run the epilogue. If the batch is an Item-α `INSERT_PROMOTED` on a source with resolved `source_join_keys`, the **bulk-INSERT** path is taken instead (§5.3).

### 4.2 DELETE (`aggregate_delete_stmts`)

Fill `<scratch>` from `base_query` with the source rewritten to `<old>`, MERGE with `Subtract` semantics (counters decrement; MIN/MAX null-then-recompute per §3). Then:

- **Dead-row cleanup**: groups whose `__ivm_count` reached `≤ 0` are deleted from the intermediate (scoped to `<affected>`) before the target sync, so they vanish from the target.
- **Bulk-DELETE early return** (§5.4): when `source_join_keys` are present and `end_query` has no further `GROUP BY`, the delete is applied directly by key and the function returns *before* the epilogue — the target rows are already gone.

### 4.3 UPDATE (`aggregate_update_stmts`)

An UPDATE is decomposed into a **subtract of the OLD image** and an **add of the NEW image**. There are two regimes:

- **Non-MIN/MAX**: the OLD and NEW deltas are *netted* in one scratch fill —
  ```sql
  INSERT INTO <scratch>
  SELECT <group_cols>, SUM(CASE WHEN sign=1 THEN col ELSE -col END) AS col, …
  FROM ( SELECT 1 AS sign, * FROM <delta_new> UNION ALL SELECT -1, * FROM <delta_old> ) u
  GROUP BY <group_cols>;
  ```
  The MERGE for this netted delta is **captured and returned** to the epilogue, which wraps it in the dispatcher DO block rather than running it inline.
- **MIN/MAX**: netting is unsafe (you'd lose which values left), so the two sides run as separate passes: fill+`Subtract` MERGE → MIN/MAX recompute (§3) → fill+`Add` MERGE → forced top-K recompute on `<shrunk>` groups. Scalar IMVs without grouping run the two MERGEs inline.

## 5. Dispatch: choosing incremental vs rebuild

Incremental maintenance is cheaper *only when the delta is small relative to the result*. When a single statement churns a large fraction of the IMV, an in-place MERGE + targeted refresh is slower than rebuilding from scratch. pg_reflex makes that decision at three points.

### 5.1 Post-scratch selectivity dispatch (`build_high_selectivity_dispatch_sql`)

The grouped UPDATE MERGE + target sync is wrapped in a `DO` block that compares affected-group count to intermediate size:

```sql
SELECT count(*) INTO _aff FROM <affected>;
SELECT GREATEST(reltuples, 1) INTO _imm FROM pg_class WHERE oid = '<intermediate>'::regclass;
_thr := COALESCE(<per-IMV wipe_threshold>, current_setting('reflex.wipe_threshold', true)::NUMERIC, 0.5);
IF (_aff / _imm) >= _thr THEN
    PERFORM reflex_reconcile('<view>');          -- rebuild (§8)
ELSE
    EXECUTE <merge_sql>; ANALYZE <intermediate>; -- incremental
    [EXECUTE <dead_cleanup_sql>;]
    EXECUTE <target_delete_sql>; EXECUTE <target_insert_sql>;
END IF;
```

The threshold resolves **per-IMV column → `reflex.wipe_threshold` GUC → compiled default `0.5`**. The `ANALYZE <intermediate>` between MERGE and target sync is **mandatory**: the MERGE shifts the `__ivm_count` distribution and, without fresh stats, the planner has chosen NestedLoop+SeqScan plans for the target DELETE that ran for 12+ minutes on 100K groups. The ANALYZE itself costs ~150 ms.

### 5.2 Pre-scratch dispatch — Path B and Path C

Both probes fire *before* the scratch fill, because on a bulk filter-flip the scratch JOIN is itself the dominant cost.

- **Path B** (`|transition| / |source| ≥ wipe_threshold`): a sweeping DML produced a transition table that is a meaningful fraction of the source ⇒ `reflex_reconcile` and skip the IMV. Cheap; gated on `source.reltuples ≥ 1000`. Misses the case where the transition is tiny but the JOIN fanout is huge.
- **Path C** (UPDATE → `INSERT_PROMOTED` only): runs `EXPLAIN (FORMAT JSON)` on the rewritten scratch-fill query (`reflex_build_path_c_explain_sql`) and reads the planner's row estimate *without executing the JOIN*. If it exceeds the IMV's threshold, dispatch to the **smart bulk-INSERT** (§5.3) which beats both reconcile and `REFRESH MV` on dim-flip fanouts. Any failure is caught and falls through to the standard incremental path.

### 5.3 Smart bulk-INSERT (`push_bulk_insert_and_affected`)

Available when the Item-α precondition guarantees the intermediate has **zero** rows for the affected keys (OLD-side filter-rejected), so a plain INSERT is correct and no MERGE probe is needed:

```sql
TRUNCATE <affected>; TRUNCATE <scratch>;
INSERT INTO <scratch> <base_query with source → <new>>;   -- only the new keys
DROP INDEX <intermediate UNIQUE>;                         -- skip per-row B-tree probes
INSERT INTO <intermediate> SELECT * FROM <scratch>;
CREATE UNIQUE INDEX … ;                                   -- rebuild bottom-up
ANALYZE <intermediate>;
INSERT INTO <affected> SELECT DISTINCT <group_cols> FROM <scratch>;
ANALYZE <affected>;
-- the epilogue then projects from intermediate (or scratch) to the target with INSERT only
```

The target only ever sees `INSERT` (`RowExclusiveLock`); the brief `AccessExclusiveLock` is on the *internal* intermediate during the index drop. Readers are never blocked.

### 5.4 Bulk-DELETE (`push_bulk_delete_via_transition`)

When the source mapping is a unique key and there is no further `GROUP BY`, the delete is applied directly by key — no scratch, no MERGE:

```sql
DELETE FROM <intermediate> WHERE (<int keys>) IN (SELECT <src keys> FROM <old>);
DELETE FROM <view>         WHERE (<tgt keys>) IN (SELECT <src keys> FROM <old>);
ANALYZE <intermediate>;
```

This returns before the epilogue (the target rows are already gone). On db_clone IN→OUT flips this is 5–11× faster than the scratch path (e.g. 54 s → 4.8 s).

### 5.5 Partition-aware dispatch (`build_partition_aware_dispatch_sql*`)

For a partitioned aggregate IMV, the dispatcher classifies partitions rather than the whole IMV:

```sql
-- group affected by partition key, resolve each to its child, compare dirty/size per child
WITH per_val AS MATERIALIZED (SELECT "<part_col>"::text AS pkey, count(*) dirty FROM <affected> GROUP BY 1),
     per_child AS (… __reflex_partition_child_for_key(parent, '<part_col>', pkey) …),
     classified AS (SELECT …, (dirty / GREATEST(reltuples, _floor) >= _thr) AS hot FROM per_child …)
SELECT array_agg(rep_key) FILTER (WHERE hot), array_agg(child_name) FILTER (WHERE hot)
  INTO _hot_keys, _hot_child_names;

IF _hot_count > _partition_total / 2 THEN PERFORM reflex_reconcile('<view>');   -- trip-cap
ELSIF _hot_count > 0 THEN PERFORM reflex_reconcile_partition('<view>', array_to_string(_hot_keys,','));
END IF;
-- cold partitions: the standard MERGE + target sync, with a hot-exclusion filter spliced in
EXECUTE <merge_sql_with_filter> USING _hot_keys [, _hot_child_names]; …
```

The hot-exclusion filter is `<part_col> <> ALL($1::TEXT[])` for **LIST** (binds hot *values*) and `__reflex_partition_child_for_key(...) <> ALL($2::text[])` for **RANGE** (binds hot *child names* — child OIDs change on the atomic swap, names don't). `_floor` (`wipe_floor_rows`) guards against never-ANALYZEd partitions reporting `reltuples = 0` and tripping an infinite ratio.

## 6. Passthrough maintenance

A passthrough IMV (`SELECT … FROM source [WHERE …]`, no GROUP BY) has **no intermediate** — the target *is* the materialised projection. Maintenance keys off whether a unique key is resolved (`mappings` present).

### 6.1 INSERT

- **Keyed**: project the new transition rows through the query and append:
  ```sql
  INSERT INTO <view> SELECT … FROM ( <base_query with source → <new>> ) ;
  ```
  No `ON CONFLICT` — the rows are new by construction.
- **Keyless**: full rebuild `DELETE FROM <view>; INSERT INTO <view> <base_query>`.

### 6.2 DELETE

- **Keyed**: delete by key read from the old transition:
  ```sql
  DELETE FROM <view> WHERE (<target keys>) IN (SELECT <source keys> FROM <old>);
  ```
- **Partitioned**: the keyed delete is run on the cold partitions with the partition-pruning predicate spliced in (`passthrough_cold_pred`), hot partitions go through the swap.
- **Keyless**: full rebuild.

### 6.3 UPDATE

- **Keyed, non-partitioned**: keyed delete of the OLD keys + delta insert of the NEW projection:
  ```sql
  DELETE FROM <view> WHERE (<target keys>) IN (SELECT <source keys> FROM <old>);
  INSERT INTO <view> SELECT … FROM ( <base_query with source → <new>> );
  ```
- **Keyed, partitioned (1.9.x)**: the hot partitions swap; the **cold path** does a true in-place upsert instead of delete+reinsert (the 1.9.1 headline):
  ```sql
  -- project the cold delta into a temp table (LIST: prune by partition key; RANGE: by child name)
  CREATE TEMP TABLE <proj> ON COMMIT DROP AS
    SELECT * FROM ( <delta_new> ) __r WHERE <cold-partition predicate>;
  -- pure-data update of the rows that stayed
  INSERT INTO <view> (<keys>, <non-key cols>) SELECT … FROM <proj>
    ON CONFLICT (<keys>) DO UPDATE SET <non-key col> = EXCLUDED.<non-key col>, … ;
  -- remove rows that disappeared or left the WHERE filter (delete-gone)
  DELETE FROM <view> __t WHERE (<keys>) IN (SELECT <source keys> FROM <old>)
    AND <cold-partition predicate>
    AND NOT EXISTS (SELECT 1 FROM <proj> __r WHERE __t.<key> = __r.<key>);
  ```
  The non-key column list is resolved at codegen time from `pg_attribute` (`resolve_inplace_non_key_cols`); if that can't run (e.g. unit-test context), the path falls back to delete+insert. The optional `reflex.assert_inplace_update` GUC re-derives the affected keys afterward and raises on any divergence from a fresh recompute — a correctness canary, off by default.
- **Keyless**: full rebuild.

The in-place upsert takes only `RowExclusiveLock` (INSERT/UPDATE, no TRUNCATE), so partitioned passthrough readers stay live.

## 7. JOIN edge cases

### 7.1 Outer-join secondary tables (`outer_join_secondary_stmts`)

When the mutated source is the **secondary** side of a LEFT/RIGHT/FULL JOIN, the naïve `L LEFT JOIN Δsecondary` delta re-emits every left row NULL-extended — double-counting non-matching left rows on INSERT and unable to express NULL semantics on DELETE/UPDATE. So these route to a targeted reconcile:

- **Passthrough, LEFT/RIGHT (1.9.0 keyed path)**: collect the changed secondary join keys (`UNION` of old+new), delete the target rows for those keys, and re-insert the base-query rows matching them — a keyed delete + delta insert, not a full rebuild.
- **Passthrough, FULL OUTER**: full rebuild (`DELETE FROM <view>; INSERT INTO <view> <base_query>`) — the FULL delta always includes unmatched rows from both sides.
- **Aggregate**: recompute is scoped to the **stable** (non-secondary-derived) group-by columns. The affected stable keys are captured, the intermediate and target rows for those keys are deleted, and both are re-derived from the base/end query filtered to those keys. If *every* group key derives from the secondary (no stable scope), it falls back to a full intermediate+target rebuild.

### 7.2 Self-join full refresh (`self_join_full_refresh_stmts`)

When the source appears 2+ times in `base_query`, a single transition table can't represent the delta of both occurrences, so the IMV is fully rebuilt from the base query: passthrough does `DELETE FROM <view>; INSERT INTO <view> <base_query>`; aggregate does `TRUNCATE <intermediate>; INSERT INTO <intermediate> <base_query>; DELETE FROM <view>; INSERT INTO <view> <end_query>`. This takes `AccessExclusiveLock` on the target.

## 8. Reconcile (full rebuild, `src/reconcile.rs`)

`reflex_reconcile(view)` is the rebuild-from-source primitive the dispatcher delegates to, and the crash-recovery entry point. Three shapes:

- **Non-partitioned aggregate**: save index DDL, drop the intermediate's indexes, `TRUNCATE <intermediate>; INSERT INTO <intermediate> <base_query>`, `TRUNCATE <view>; INSERT INTO <view> <end_query>`, recreate the reflex-managed indexes and any user indexes, `ANALYZE`.
- **Non-partitioned passthrough**: drop target indexes, `DELETE FROM <view>; INSERT INTO <view> <base_query>`, recreate indexes, `ANALYZE`.
- **Partitioned**: iterate the source partition tree and run a per-child **atomic DETACH/ATTACH swap** — build a new child outside the tree, fill it from `(base_query) WHERE <partition constraint>`, add a matching `CHECK` (so PG skips the ATTACH validation scan), then in one sub-transaction `DETACH` old + `ATTACH` new + `DROP` old + `RENAME` swap→canonical. The intermediate is swapped before the target (the target fill reads the intermediate). `AccessExclusiveLock` on the parent is held only for the µs-scale DDL window, not the data fill. See [internals → Atomic swap](internals.md#atomic-swap-160-planspartitioning_3md-1).

`reflex_reconcile` also runs `reflex_sync_partitions` at entry (defense-in-depth) and cascades to dependent IMVs.

### 8.1 Source TRUNCATE (`reflex_build_truncate_sql`)

A `TRUNCATE` on the source emits `DELETE FROM <view>` (and, for aggregate IMVs, `TRUNCATE <intermediate>`). The target sees a `DELETE`, not a `TRUNCATE`, so concurrent readers keep running against MVCC-visible rows until the writer commits.

## 9. Deferred mode (`src/trigger/deferred.rs` · `reflex_flush_deferred`)

In `DEFERRED` mode the per-statement trigger only **stages** the delta into `__reflex_delta_<source>` (tagged `I` / `D` / `U_OLD` / `U_NEW`) and enqueues the source in `__reflex_deferred_pending`. The actual maintenance runs once at COMMIT (or on-demand via `reflex_flush_deferred(source)`):

1. **Per-source flush lock** — `pg_advisory_xact_lock(hashtext('reflex_flush:<source>'))` serialises concurrent flushes of the same source; different sources don't contend.
2. **Net the staged delta** — the new and old images are reduced with `EXCEPT ALL` (multiset difference), so a row inserted-then-deleted, or an UPDATE that didn't change the projected columns, cancels out before any maintenance runs (spurious-update short-circuit).
3. **Cross-source double-count guard** — if a single transaction mutated **2+ sources** of the same join IMV, the per-source deltas would double-count `ΔA ⋈ ΔB`. Such IMVs are **fully reconciled once** for the batch (tracked in a temp `__reflex_deferred_reconciled_batch` marker) instead of incrementally maintained per source.
4. **Per-IMV maintenance** — each IMV drains through the same `UPDATE`-shaped delta builder as IMMEDIATE mode, wrapped in its **own `DO`/SAVEPOINT** block: a failure (e.g. a target constraint violation) is recorded in `__reflex_ivm_reference.last_error` and the next IMV still runs, rather than aborting the whole transaction's cascade.
5. **Cleanup** — clear `__reflex_delta_<source>` and the pending row.

See [deferred mode](deferred-mode.md) and [crash recovery](../operations/crash-recovery.md) for the operator-facing view.

## 10. Operation matrix

The full routing, as a single table. "Target lock" is the lock the path takes on the user-queried target (see [delta-processing → Locking](delta-processing.md#locking-and-reader-impact) for the complete table).

| Shape | Operation | Path | Emitted spine | Target lock |
|---|---|---|---|---|
| Aggregate | INSERT | MERGE-Add | scratch→MERGE(+)→affected→epilogue | RowExclusive |
| Aggregate | INSERT (promoted, join-key) | bulk-INSERT | scratch→drop idx→INSERT→reindex→INSERT target | RowExclusive |
| Aggregate | DELETE | MERGE-Subtract | scratch→MERGE(−)→dead-cleanup→epilogue | RowExclusive |
| Aggregate | DELETE (join-key, no rollup) | bulk-DELETE | keyed DELETE intermediate + target | RowExclusive |
| Aggregate | UPDATE | netted MERGE + dispatch | scratch(net)→affected→dispatcher DO | RowExclusive *or* AccessExclusive (if reconcile) |
| Aggregate (MIN/MAX) | UPDATE | subtract→recompute→add→shrunk recompute | two-pass MERGE + scoped source scan | RowExclusive |
| Aggregate (partitioned) | UPDATE | partition-aware dispatch | classify hot/cold → swap hot, MERGE cold | per-child AccessExclusive (DDL window) + RowExclusive |
| Passthrough | INSERT | keyed append | `INSERT INTO <view> SELECT … <new>` | RowExclusive |
| Passthrough | DELETE | keyed delete | `DELETE … WHERE key IN <old>` | RowExclusive |
| Passthrough | UPDATE | keyed delete + delta insert | delete OLD keys, insert NEW projection | RowExclusive |
| Passthrough (partitioned) | UPDATE | in-place cold upsert (1.9.1) | `INSERT … ON CONFLICT DO UPDATE` + delete-gone; hot swap | RowExclusive + per-child DDL |
| Outer-join secondary (LEFT/RIGHT) | any | keyed targeted reconcile | delete+reinsert changed keys | RowExclusive |
| Outer-join secondary (FULL) | any | full rebuild | `DELETE FROM <view>; INSERT <base_query>` | RowExclusive |
| Self-join | any | full refresh | TRUNCATE+rebuild | AccessExclusive |
| any | TRUNCATE source | truncate handler | `DELETE FROM <view>` (+TRUNCATE intermediate) | RowExclusive |
| any | dispatch ≥ threshold | reconcile | drop idx→TRUNCATE→rebuild→reindex (or per-child swap) | AccessExclusive (non-partitioned) |
